## What V0.6.0-beta.2 changes (vs beta.1)

Installer reliability (B01–B12):

- Registration mutations reconcile after failure/timeout: a failed `opencode
  plugin add` re-lists before deciding recovered vs failed vs unknown; no
  blind retries; registration is idempotent.
- Global inspection is tri-state (registered / absent / unknown). A timed-out
  `plugin list` (now 30s, neutral cwd) never reports "absent".
- Operation-specific timeouts with preserved exit codes, timeout flags, and
  sanitized diagnostics (inspection 15s, list 30s, mutations 90s,
  package install 300s, backup/apply 120s, bridge 180s, registry 20s).
- Fresh-install Spicetify backup: `apply` runs `backup` first only when the
  backup directory is missing, and retries once on backup-related failures.
  Valid backups are never overwritten; `restore` stays manual.
- `status` never mislabels a prerelease `latest` tag as "Latest stable".
- Compact environment summary at setup start; invalid confirmations re-prompt
  (default still "no"); cancellation reports completed/pending/skipped.
- Optional host-provided TUI peers (`peerDependenciesMeta.optional`) so CLI-only
  installs on Node 22/24 do not pull engine-26-only OpenTUI; packed tarball
  still verified (placeholder secret, no stray 64-hex, isolated install).
- Narrow-sidebar connection labels stay concise with actionable hints; TUI
  startup retry extended to ~18s for slow bridge readiness (loopback auth
  unchanged).

Coexistence (B13): global-only and local-only installs work; when both are
configured the installer warns and never edits project config. The OpenCode
host activates the first copy in boot order and marks the other `Duplicate
plugin ID` (failed) without running its `setup()` — there is no
host-supported prefer-local dedupe and no port race from the loser.
Documented limitation: remove one entry (or `-`-disable) and restart OpenCode.

Spicetify + onboarding 2.0 (B14–B18): Winget source refresh, trusted-version
resolution with upstream-vs-Winget drift warnings, post-install verification,
and a unified menu (update both / plugin-only / Spicetify-only / repair /
continue / exit). No unsigned remote-script execution; no package-manager
mixing; themes/extensions/credentials preserved.

CI (Phase 4): 4 parallel jobs (Linux fast checks, Windows fast unit subset,
Windows+Bun rendering, Windows pack verification), npm + Bun caches,
concurrency cancel-in-progress, path filters, per-job timeouts. See
`docs/CI_PROFILING.md` for before/after evidence.

Public readiness (Phase 5): audit report in `docs/PUBLIC_READINESS.md`.
Checklist (CONTRIBUTING, SECURITY, templates, Dependabot) added; visibility
change still requires explicit approval (not done).

## What V0.6.0 is

The first distribution milestone. Player behavior is unchanged from V0.5.7;
all V0.6.0 work is packaging, installation, verification, and release
engineering:

- `bin/opencode-spotify.js` CLI entry (`setup`, `status`, `update`, `repair`,
  `doctor`, `uninstall`, plus `--dry-run` / `--yes` / `--json` / `--offline`
  and other safety flags). It runs a compiled `dist/cli` build because Node
  refuses to type-strip files installed under `node_modules`.
- Global registration through the native
  `opencode plugin add opencode-spotify@<version>` command. One package entry
  loads both server and TUI; project configuration is never edited by the
  installer.
- Windows environment detection for OpenCode, Spotify Desktop (including the
  Store caveat), Spicetify (PATH/LOCALAPPDATA, owner, config), existing
  registration, bridge files/credential shape (never printed), port ownership,
  and compatibility.
- First-time onboarding with automatic (winget or verified official script) or
  manual Spicetify installation, explicit confirmations, recheck paths, and
  clean cancellation.
- Plugin-only and combined Spicetify updates, repair, diagnostics, uninstall,
  dry-run, and a pinned plugin version to keep the bridge coordinated.
- `scripts/verify-package.mjs` builds the CLI and provisioner, packs, audits
  the file list, installs the tarball in isolation, and exercises the installed
  `--version` / `--help`.
- `tests/package-smoke.test.ts` runs that verification inside `npm test`.
- Windows CI gains the verify step; a manual, OIDC-based
  `.github/workflows/release.yml` is prepared but disabled by default with a
  repository-variable kill switch.
- `LICENSE` (MIT) added at the repository root and in `plugin/` so the
  tarball carries it.
- `docs/DISTRIBUTION.md` documents registration, updates, rollback,
  compatibility, trusted publishing, and QA gates.

## First publication and dist-tags

npm gives the first published version the `latest` tag even when `--tag beta`
is used. To keep stable `latest` from pointing at an unverified build:

1. First publish a prerelease such as `0.6.0-beta.1` under `beta` (manual
   `npm login` + 2FA; OIDC cannot bootstrap a package that does not exist).
2. Test with `npx opencode-spotify@beta` and complete physical QA.
3. Build the stable `0.6.0` artifact (version metadata differs), rerun all
   automated checks, publish it, and move `latest` to it.

The release workflow cannot be used for the very first publish. After the
package exists, configure trusted publishing with the `release.yml` workflow
and the `npm-release` environment, set `NPM_PUBLISH_ENABLED=true`, and use the
manual dispatch for subsequent releases. Provenance is omitted while this
GitHub repository is private.

## Compatibility

Protocol 2 / auto-1, OpenCode ≥ 2.3.0, Spicetify ≥ 2.0.0, Node ≥ 22.18.
Exact-version pinning (`opencode-spotify@<version>`) is intentional so the
plugin and installed bridge remain coordinated. A local development
registration is never silently replaced by an update.
